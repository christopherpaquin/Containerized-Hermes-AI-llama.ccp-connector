**Task:** Build a reproducible Docker Compose deployment of Hermes Agent (gateway + dashboard) wired to a native, host-run llama.cpp llama-server, with no cloud inference provider ever configured.

**Decision:** Followed NousResearch/hermes-agent's own root `docker-compose.yml` architecture as closely as possible (two services, `network_mode: host`, `~/.hermes:/opt/data`, `HERMES_UID`/`HERMES_GID` defaulting to 10000) but swapped its `build: .` for the published `nousresearch/hermes-agent` image, pinned to `v2026.8.13` (exact tag, not `latest`/`main`, per repo image-pinning policy). Model provider is configured via Hermes's own `hermes config set model.{provider,base_url,default,api_key}` CLI (not hand-edited YAML), run inside the gateway container via `docker exec hermes`.

**Why:** The repo's own compose file is the most authoritative source for "current official architecture" (more so than a docs-page example that showed a different single-container pattern). Using the official `hermes config` CLI avoids re-implementing YAML-merge/migration logic Hermes already owns, and backs up `config.yaml` automatically only when a change is actually about to happen (verified idempotent across 3+ `./deploy.sh` runs - no duplicate backups, no config churn).

**Progress:** Deployed and verified end-to-end on this host: llama.cpp confirmed running with `--jinja` and `n_ctx=65536` (meets Hermes's hard 64K minimum for tool use), `deploy.sh`/`healthcheck.sh`/`status.sh`/`uninstall.sh` all pass `bash -n` + shellcheck clean, `docker compose config` validates, and `docker exec hermes hermes -z "Reply with exactly: HERMES_LLAMA_OK"` succeeded - proving the full Hermes -> llama.cpp -> model path, not just llama.cpp in isolation. `uninstall.sh --purge`'s typed-confirmation guard was verified to abort safely on a mismatched confirmation. No cloud provider API key is ever written to `~/.hermes/.env`; documented in README why that (plus `auxiliary.*` defaulting to the main/local model) is the actual guardrail against accidental cloud fallback, since Hermes's `fallback_providers` is opt-in and not touched by this deployment.

## 2026-08-16 03:37
**Task:** User asked to expose the Hermes dashboard on 0.0.0.0 (LAN) instead of the 127.0.0.1-only default.

**Decision:** Added optional `HERMES_DASHBOARD_BASIC_AUTH_USERNAME`/`_PASSWORD`/`_SECRET` passthrough in compose.yaml, and a `check_dashboard_auth` step in deploy.sh that (a) refuses to proceed with a non-loopback `HERMES_DASHBOARD_HOST` unless username+password are already set in `.env`, and (b) auto-generates `HERMES_DASHBOARD_BASIC_AUTH_SECRET` via `openssl rand -hex 32` the first time it's needed, idempotently (verified stable across a repeat `./deploy.sh` run). healthcheck.sh and status.sh were updated to probe `127.0.0.1` instead of a literal `0.0.0.0` destination (kernel treats 0.0.0.0 as non-connectable as a destination in some contexts) via a new `dashboard_probe_host`/`is_loopback_host` helper pair in common.sh, and healthcheck.sh now asserts an unauthenticated request against a non-loopback bind does NOT return HTTP 200 -- i.e. that the auth gate is actually enforced, not just configured.

**Why:** Hermes hard-refuses to start a non-loopback dashboard without a registered auth provider (a documented response to a real prior incident: an unauthenticated public dashboard was the entry point for a backdoor campaign). Rather than let deploy.sh fail opaquely inside the container, it now fails fast on the host with a clear message telling the operator what env vars to set. `.env.example` keeps `HERMES_DASHBOARD_HOST=127.0.0.1` as the committed default -- LAN exposure is opt-in per-deployment via the gitignored `.env`, so the secure default is preserved for anyone else who clones this repo.

**Progress:** Redeployed with `HERMES_DASHBOARD_HOST=0.0.0.0` and user-supplied basic-auth credentials (username `admin`; the user chose their own password after being warned it should be strong -- they picked a weak one anyway, noted back to them but not overridden). Verified: dashboard now returns HTTP 302 (redirect to a session/cookie-based `/login` page) instead of 200 for unauthenticated requests, `docker compose config` validates, shellcheck clean, and a second `./deploy.sh` run left the generated secret unchanged (idempotent). Did not script-verify the actual login form POST (field names undocumented) -- only that the gate itself is active.

## 2026-08-16 13:06
**Task:** Wire up Slack as a chat platform for Hermes (user's choice after declining Telegram), using Socket Mode so no inbound port/public webhook is needed.

**Decision:** Added a `configure_slack` step to deploy.sh, gated on `SLACK_BOT_TOKEN` being set in `.env`. `SLACK_BOT_TOKEN`/`SLACK_APP_TOKEN` route correctly through `hermes config set` (Hermes recognizes them as secret-shaped keys and writes them to `~/.hermes/.env`), but `SLACK_ALLOWED_USERS` does not -- `hermes config set SLACK_ALLOWED_USERS ...` silently misfiled it as a stray unrecognized top-level key in `config.yaml` (with a `not a recognized config key` warning) instead of `~/.hermes/.env`, where the docs say it belongs. Fixed by writing `SLACK_ALLOWED_USERS` directly into `~/.hermes/.env` via the same `upsert_env_var` helper used for this repo's own `.env`, and by comparing idempotency against `~/.hermes/.env` directly for that one var (not `hermes config get`, which doesn't know about it either).

**Why:** Trusting the CLI's own "not a recognized config key" warning at face value would have shipped a broken allowlist -- Hermes's default is deny-all-unknown-senders, so a misfilfiled `SLACK_ALLOWED_USERS` could either silently not work, or (worse, unverified either way) accidentally rely on undocumented config.yaml-to-env bridging behavior. Went with the documented-correct location instead of assuming the bridging behavior was reliable.

**Progress:** Deployed with real user-supplied Slack tokens (xoxb-.../xapp-.../member ID collected interactively over several turns). Confirmed via `docker logs hermes` that the "No env user allowlists configured" warning stopped appearing after the fix landed. Also fixed a startup-race: `hermes gateway restart` (triggered by new Slack config) needs the same `wait_for_port` treatment as the initial gateway start before the API server port is reliably reachable -- healthcheck.sh caught this immediately (failed on `Gateway API server port ... not accepting connections`) both before and after the first fix attempt, which is exactly the kind of real regression this healthcheck is meant to catch, not paper over. Third `./deploy.sh` run confirmed fully idempotent: "Slack already configured with the current tokens; skipping", zero restarts, all health checks pass. Surfaced to the user (not yet actioned): Hermes's own gateway log warns that a network-accessible API server (0.0.0.0) combined with `terminal.backend: local` means anyone reaching the API server or Slack bot can run unsandboxed host-user shell commands -- offered to switch to `terminal.backend: docker` given Slack is now an internet-reachable surface, awaiting the user's decision.
